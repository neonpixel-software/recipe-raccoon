# Phase 4: Settings & iCloud sync — history

The dated notes for Phase 4, moved out of [PLAN.md](../../PLAN.md) word for word (#217): checks on devices, issue fixes and TestFlight stages, in the order they were written. Older notes can describe a state a later note replaced; PLAN.md has the current status.

## 4.1

**Settings screen with storage toggle**

Acceptance: switching to iCloud migrates existing recipes and they appear on a second signed-in device/simulator; switching back leaves a local-only copy.

Note: the model schema (`RecipeModel`, `IngredientLineModel`, `TagModel`, `DensityEntryModel`) was reworked ahead of this phase (issue #48) to be CloudKit-compatible — no `.unique` attributes, every attribute has a default, every relationship is optional with an inverse declared on both sides. Verified via a regression test (`CloudKitSchemaCompatibilityTests`) that loads all four models into a CloudKit-backed `ModelContainer` without throwing. Implemented (design: `app/docs/plans/2026-09-30-phase-4-1-icloud-sync-design.md`): a Local store and an iCloud store (private CloudKit database `iCloud.com.neonpixel.reciperaccoon`), a Settings screen (a sheet on iOS/iPadOS, the Settings window on macOS) that switches between them live. Switching up merges local recipes into iCloud; switching back replaces the local store with a snapshot of iCloud. Preset tags seeded on several devices are merged after each CloudKit import. The signing team and iCloud entitlements live in the gitignored `app/Config/Signing.xcconfig` (see `Signing.xcconfig.example`), because the repo is public. Builds without it (CI) have the setting disabled. The macOS app is now sandboxed.

Device check (2026-09-30, Mac + iPhone 12, development builds): adding and deleting recipes syncs both ways, switching to iCloud merges local recipes up, preset tags created on both devices are merged, and the iPhone shows Mac edits live. Left unchecked because on the Mac, iPhone edits only appear when the app is launched, brought to the front or makes an edit, not live. The Mac's push service only polls the development push environment every 13–24 minutes (`sandbox.push.apple.com`, "Push is connected? NO … pollInterval" in the apsd log), and CloudKit's pushes arrive only at those polls. A plain-SwiftData control app with the same app ID behaved identically, so the app code isn't the cause. Production pushes arrive at once on the same Mac, so check this again on the first TestFlight build (12.4). The simulator can't be the second device while the Apple ID has Advanced Data Protection on (CloudKit reports the account as temporarily unavailable), so use a real device.

Checked off 2026-10-15 on the `v1.0.1` TestFlight builds (12.4 Stage 1): an iPhone edit appeared in the Mac window, already open and in front, after about a minute without clicking it. On `v1.0.0` it only appeared after a click, because the Mac app never called `registerForRemoteNotifications()`: `apsctl status` listed the iCloud container topic as nonwaking and apsd held its pushes. `MacAppDelegate` (#209) registers at launch in builds with iCloud, and on 1.0.1 the topic is enabled on the production push connection, with pushes arriving.

Schema changes after the first CloudKit build ships need migration planning: CloudKit's production schema only allows adding fields, never renaming or removing them, and older app versions keep syncing records without the new fields. Until that build ships, attributes can still be added freely (e.g. `RecipeModel.equipment`, #82). Before shipping it, deploy the development schema to production with every attribute the first release needs, and plan later model changes around additive fields.

## 4.2

**Sync status in Settings**

Acceptance: a failed export shows an error within a few seconds, both in a test that posts a failed event and in the app; healthy sync shows the time of the last successful sync; nothing changes while storage is Local; all new text is in the five languages.

Built 2026-10-24: `CloudKitSyncMonitor` (Data) follows `NSPersistentCloudKitContainer.eventChangedNotification`, which SwiftData's CloudKit store posts, keeps the latest finished setup, import and export event, and turns them into an `ICloudSyncStatus` (Domain): waiting for the first sync, last synced at a time, or failed. The most recent failure shows while any kind's latest event failed, and one that needs the user (storage full, not signed in, stopped) wins over a temporary one; a later success of the same kind clears it. Errors are classified by the most telling CloudKit error inside them (partial failures and `NSUnderlyingErrorKey` included): storage full (`quotaExceeded`), not signed in (`notAuthenticated`, `accountTemporarilyUnavailable`, Core Data 134400), temporary (offline, busy, rate limited: shown in grey, since CloudKit retries) and stopped (anything else, such as #207's schema error: close and reopen the app). Errors show in red with Copy Error Details, which copies the raw error for an issue report. The monitor starts before the store opens, so it sees the setup event. The new strings in four languages are drafts for the native-speaker check. Left: the in-app check on a TestFlight build in iCloud mode, since the unit tests post fake events and can't prove SwiftData posts the real ones: "Last synced" within seconds of launch; airplane mode shows the grey waiting row and signing out of iCloud the red one; switching to On This Device hides the row, and switching back still updates it.
